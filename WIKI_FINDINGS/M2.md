# wowdev.wiki findings — `M2` (main page)

Current, correct facts only — corrections/additions to wowdev.wiki's `M2`
page that husk's own reverse-engineering turned up, distilled from the full
investigation. **For the evidence behind any fact below** (real files
checked, byte-level walks, what got corrected along the way), see the
matching numbered section in `../WIKI_FINDINGS_HISTORY.md` — the section
numbers here match that file's exactly, nothing renumbered.

Confidence tags follow the same convention as the rest of this tree:
**verified** (checked against real game files), **inferred** (structurally
justified, not independently cross-checked), **hypothesis** (plausible, not
confirmed).

Sibling per-page files: `M2/anim.md` (`.anim`), `M2/skel.md` (`.skel`),
`M2/skin.md` (`.skin`), `../BONE.md`, `../PHYS.md`.

---

## `M2Sequence` is 0x40 (64) bytes — verified — history §1

`M2Bounds bounds` is a real, live 28-byte field in the struct (not a stale
annotation); total record size is **64 bytes**. The wiki's own `/*0x20*/`
comment on the following field, `variationNext`, is wrong/unrenumbered —
trust field-list order over that one inline offset comment. `aliasNext` (see
below) sits at the corrected offset **0x3E**, not the wiki's literal 0x22.

## `M2/.anim`'s `AFM2` chunk shape — see `M2/anim.md`

Moved to its own page; the finding is entirely about a `.anim` sidecar file,
not the `M2` container itself.

## `bounding_box` is a containment bound, not a tight fit — hypothesis (why) — history §5

The header's `bounding_box` is **not** a tight AABB around the bind-pose
mesh on any axis, in either real file checked (~2x per-axis on
`bloodelffemale.m2`, ~4x on `bloodelffemale_hd.m2`). What *does* hold with
no exceptions: the bind-pose mesh's own AABB is fully **contained** inside
`bounding_box`, per axis. Likely explanation (not confirmed against an
authoritative source): the box covers the model's full *animated* range, not
just rest pose. `tests/test_conformance.cpp` checks containment, not
tight-fit equality.

## `M2Particle` Cata+ byte offsets + `FBlock` timestamps — verified — history §6

Post-`childEmittersModelFilename` `M2Particle` fields (hand-derived,
matching the wiki's own independently-stated total size exactly): the
Cata+ shape is **476 bytes** default, **492 bytes** with the
`multiTexScrollMid`/`multiTexScrollRange` wrapper (`flag_use_texture_combiner_combos`-adjacent
version gate, `kMinVerifiedParticleVersion = 272`). `FBlock` (Wrath+
color/alpha/scale/UV curves) timestamps are **`uint16_t`**, not the
`uint32_t` a real `M2Track` uses, decoding as a clean `0..0x7FFF` run —
likely a normalized lifetime fraction (hypothesis, exposed raw, not
rescaled).

## `WFV3` has a real, undocumented 64-byte short variant — verified — history §8

All 9 real `WFV3`-bearing files in a 130k-file corpus are exactly 64 bytes,
missing the trailing `unk1`-`unk4` floats the wiki's 80-byte struct
documents. `dumpWfv3` reads those four fields conditionally on
`c.size >= 0x50`, `null` otherwise.

## `WFV1`/`WFV2`/`DPIV`/`AFRA`/`PCOL` are real and present — verified — history §10

An earlier "zero real files" result for all five tags was a real scanner bug
(`bytes` vs `str` comparison always `False`), not a real absence — corrected
via an independent `casc-tool scan-chunks` run. Real counts in the same
130,576-file corpus: `WFV1` 2, `WFV2` 2, `AFRA` 32, `DPIV` 2,632, `PCOL`
2,354. All five now have real structural parsing in `husk dump-chunks`
(`dumpWfv1`/`dumpWfv2`/`dumpDpiv`/`dumpAfra`/`dumpPcol`, `src/cmd_dump.cpp`) —
`AFRA`/`WFV1` are a fixed 16-byte struct (one float + 12 zero bytes); `DPIV`
is a real record array (`chunk.size / 32` records, 8×float32, last 4 always
zero); `PCOL` is a real self-describing four-region (position/normal/index/
flags) collision struct, each region read via its own offset field (regions
aren't always contiguous — a real file has an 8-byte gap between two of
them). `WFV1`/`WFV2` remain a thin 2-file sample, flagged tentative.

## `DETL`'s real stride is 12 bytes, chunk zero-padded to 16 — verified — history §11

The wiki's field list sums to 12 bytes but its own `/*0x0a*/` offset comment
says 10 — the field list is right, the comment is wrong (same "trust the
field list" resolution as `M2Sequence` above). **New, undocumented**: the
chunk's total byte size is zero-padded up to the next 16-byte boundary
(`((12 × lights.count + 15) / 16) × 16`), confirmed against all 1,043 real
`DETL`-bearing files, 100% match. `lights.count` itself needs no correction.

## `M2Sequence.aliasNext` is a local array index — verified — history §12

`aliasNext` is a plain index into the *same file's* own `sequences` array
(`sequences[aliasNext]`), not an `AnimationData.dbc` id, confirmed on 157
real alias sequences across 4 real character files — the chain-walk
(`aliasNext` repeatedly until a sequence without `flags & 0x40`) always
terminates cleanly, no cycles. Read at the wiki's literal, pre-correction
`/*0x22*/` offset (before this file's own `M2Sequence`=64-byte correction
above), the field lands inside `M2Range replay` instead and produces
nonsensical values — the real offset is **0x3E**. `buildAnimations` now
resolves the chain into real clips, but must check `flags & 0x20` ("stored
inline") *before* treating a sequence as needing chain resolution — 31 of
`bloodelffemale_hd.skel`'s 38 alias sequences also carry `0x20` and already
have real data of their own.

## `EXP2`/`PFDC` real files exist; `BLP2` "anomaly" was a listfile mismatch — verified — history §13

Both `EXP2` (17,065 real files) and `PFDC` (2,430 real files) are genuinely
present — the earlier "zero real files" claim was a local-extraction gap in
this project's own corpus, not a real absence; both parsers already handled
real data correctly once pulled and tested, no code changes needed. A
reported 1-byte `BLP2` top-level chunk in one `.m2`-masked file resolved to
a real BLP2 **texture**, not an M2 file at all — a listfile/FileDataID
labeling mismatch upstream, not a husk bug (husk already refused to open it
outright, correctly). 8 real `.m3` files exist elsewhere in the corpus — an
entirely different, undocumented format, out of scope by design.

## `global_flags` decoded, `textureCombinerCombos` implemented — verified — history §14

`global_flags`' every wiki-named bit is decoded (`m2::globalFlagNames`),
cross-checked against real `.phys`-presence (`flag_load_phys_data`) and
confirmed as a real OR, not a contradiction (`flag_new_particle_record` vs.
`version > 271` — the wiki's own text already says "or"; husk's existing
version-only gate was already correct). `Header::textureCombinerCombos`
(offset 0x130, gated on its flag bit) is implemented but has **zero real
corpus hits** in a 130,576-file scan — the byte layout is unambiguous and
low-risk regardless, but this specific table is unverified against real
data. `resolveSkin`'s failure messages now name the exact candidate path
tried, not just the directory searched.
