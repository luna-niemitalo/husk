# WoW client shaders, exported

Every shader container the client ships (`<corpus>/shaders/**/*.bls`),
unpacked to one directory per container. Each distinct compiled program is
written as a standalone DXBC file, plus listings in two families:

- **Direct3D** (the form the client ships): D3D assembly for shader model
  5, DXIL/LLVM IR for shader model 6.
- **Vulkan/Linux** (the form vkd3d-proton runs on Linux): SPIR-V, its text
  form, and GLSL decompiled from it.

Generated by `tools/export_shaders.py` (this README is copied from
`tools/export_shaders_README.md`; edit it there). Container layout facts
and wiki corrections: `WIKI_FINDINGS/BLS.md`.

```
direnv exec . tools/venv/bin/python -I tools/export_shaders.py
```

A rerun skips every container whose `manifest.json` exists. To redo one,
remove its directory.

## What came from what

| File | Answers |
|---|---|
| `mapping.csv` | one row per exported container: source `.bls` path (listfile spelling), its FileDataID, the GFAT entry it was unwrapped from (if any), output directory, slot/blob counts, and how many of each listing succeeded |
| `index.json` | the same rows as JSON |
| `<dir>/manifest.json` | everything about one container (below) |
| `errors.log` | `.bls` files that could not be exported at all, one per line |

Directory names mirror the source: `shaders/pixel/dx_5_0/illum.bls` →
`pixel/dx_5_0/illum/`. A GFAT file (`shaders/pixel/material3_wmo_ps.bls`)
wraps one container per graphics API. Each one is unwrapped into the same
shape, e.g. `pixel/dx_5_0/material3_wmo_ps/` and
`pixel/dx_6_0/material3_wmo_ps/`, with `gfat` set in its manifest.

## Per-container layout

```
<stage>/<api>/<name>/
  manifest.json
  blobs/NNNN.dxbc      the compiled program, a complete DXBC container
  asm/NNNN.asm         dx_5_0: Direct3D shader-model-5 assembly (vkd3d-compiler)
  asm/NNNN.ll          dx_6_0: DXIL as LLVM IR, with signatures and bindings (dxc -dumpbin)
  spirv/NNNN.spv       SPIR-V binary (vkd3d-compiler)
  spirv/NNNN.spvasm    SPIR-V text (spirv-dis)
  glsl/NNNN.glsl       GLSL 450 decompiled from the SPIR-V (spirv-cross)
  */NNNN.*.err         the tool's stderr where it failed; later steps of that chain are not run
```

`<stage>` is `vertex`, `pixel`, `geometry`, `compute` or `raytracing`.
`<api>` is `dx_5_0` (shader model 5, DXBC-TPF bytecode) or `dx_6_0`
(shader model 6, DXIL bytecode). They hold the same shaders compiled
twice: where both have a slot table, the compiled slots are identical, so
a slot index names the same permutation in both. The blob numbering can
differ, because each side merges identical programs separately. A few
shaders exist only in `dx_6_0` (they use SM6-only features), and the
five `0x1000C` containers under `dx_5_0` hold DXIL despite the
directory name.

### `manifest.json`

| Field | Meaning |
|---|---|
| `source` | absolute path of the `.bls` this came from |
| `gfat` | `{api, start, end}` byte range inside a GFAT file, or `null` |
| `version`, `api`, `header` | container header fields (`header` holds the raw counts, plus the fields whose meaning is unknown) |
| `slots` | one entry per permutation slot: the index of the blob compiled for it, or `null` for an uncompiled slot. `null` overall for `0x1000C` containers, which have no decoded slot table |
| `slot_hashes` | each slot's 16-byte hash as hex. What it hashes is unknown |
| `blobs[]` | one per distinct program: `file`, the `slots` that use it, `stream_offset` in the inflated stream, the raw `block_header` hex, `dxbc_size`, `trailing_bytes`, the DXBC `parts`, and per-listing `{file, status}` under `listings` |

A permutation slot is the client's index for one combination of shader
features. Many slots share one blob. Which feature bits make up a slot
index is not known yet.

## The formats, outside in

1. **GFAT** (`TAFG` on disk): `magic, version 0x1000B, u32 count`, then
   `count × {api fourcc reversed ("05XD" = DX50), start, end}`. Each range
   is an ordinary GXSH file.
2. **GXSH** (`HSXG` on disk), version `0x1000E`: a 40-byte header (`magic,
   version, api, nPermutations, nShaders, ofsChunks, nChunks, ofsData,
   unk0, unk1`), `nShaders` 24-byte slots `{offset, size, hash[16]}`, the
   inflated stream length, then `nChunks+1` chunk offsets. The chunks are
   separate zlib streams; inflated and concatenated, they form one stream,
   and the slot offsets index into it.
3. **Block**: each slot's bytes are a 96-byte block header (unknown
   fields, kept as hex), then a DXBC container, then 0 or 4 padding bytes.
4. **DXBC**: Microsoft's shader container. `DXBC, checksum[16], version,
   total size, part count, part offsets`, then fourcc-tagged parts:
   `SHEX` (SM5 bytecode) or `DXIL` (SM6 LLVM bitcode), plus signatures
   (`ISG1`/`OSG1`/`PSG1`), resource definitions (`RDEF`), statistics
   (`STAT`), hashes (`HASH`) and so on. Any DXBC tool can read
   `blobs/*.dxbc` directly.

## Using these on Linux

Every tool below is in the husk dev shell (`direnv exec . <cmd>`).

- Read a program: `glsl/NNNN.glsl` is the most readable form. The
  client's shaders are stripped of names, so constant buffers come out as
  `cbN_N` blocks holding one `vec4` array, and textures as
  `SPIRV_Cross_Combined<texture><sampler>`. The register numbers
  match the D3D listing's `cbN`/`tN`/`sN`.
- Re-decompile into another language from the SPIR-V: `spirv-cross
  spirv/NNNN.spv --hlsl` (or `--msl`, `--version 330`, `--es`).
- Validate or optimize SPIR-V: `spirv-val`, `spirv-opt`.
- Re-disassemble a blob: `vkd3d-compiler -x dxbc-tpf -b d3d-asm` (DX50),
  `dxc -dumpbin` (DX60).
- DXIL blobs often have no SPIR-V or GLSL. vkd3d-compiler 2.0 can't read
  barycentric inputs (`E8016: DXIL semantic kind 28`) or wave ops, so most
  `dx_6_0` blobs stop after the dxc listing. For GLSL, use the `dx_5_0`
  twin of the same shader and slot (see above).
